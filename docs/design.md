## Overview

Wraps the FAA Air Traffic Control System Command Center (ATCSCC) status feed behind the public NAS Status dashboard (`nasstatus.faa.gov`) and the ATCSCC advisories database (`www.fly.faa.gov/adv`). It answers "why are flights into X delayed, how long, and what does the FAA expect next": active ground stops, Ground Delay Programs (GDP), Airspace Flow Programs (AFP), arrival/departure delays, airport closures, deicing, runway configuration and arrival rate, the daily operations plan, and the advisory text behind each program. A bundled snapshot of the FAA's airport identifier registry (NASR) validates airport codes and names the airport each code resolves to.

Audience: airline operations coordinators and dispatchers, corporate travel managers, aviation journalists, and travel-assistant agents forecasting disruption. Out of scope: per-flight EDCTs and gate or ticket status (not in the feed), live aircraft positions, weather observations and forecasts, and NOTAM search beyond the closure text the feed carries.

## Requirements

- Read-only, keyless, public data. FAA operational status and NASR airport data are US federal works (17 U.S.C. §105, public domain): hosting, caching, bundling, and redistribution are unrestricted, and no attribution is required. Credit the FAA as a courtesy in the README.
- The status upstream is the dashboard's own undocumented backend: no published schema, terms, or rate limits. Parse tolerantly. Classify a shape change as a typed error distinct from an outage.
- No published rate limit. The dashboard polls each endpoint once a minute per open tab, and the FAA states data "updates occur every minute". The server caches each feed for 60 s, shares one in-flight request per endpoint, and paces itself below a busy browser tab's rate (see Services).
- Deployment: stdio and hosted HTTP. No `ctx.requestInput`, so `sessionMode: 'stateless'` is safe. No DataCanvas or Mirror, so the design is Workers-portable, but Workers is not a target.
- No server env vars, credentials, or auth scopes (`MCP_AUTH_MODE=none` for hosting). Nothing is fetched from the NASR host at runtime; the airport directory is regenerated by a script at maintenance time.
- Every time is UTC ISO 8601 as the feed supplies it. Airport times are never converted to local. Pacing airports carry an IANA-style `timezone` (`US/Pacific`) so a caller can convert.

## User Goals

1. Check whether an airport has an active delay program, ground stop, delay, or closure, with average/maximum delay minutes and the stated cause → `faa_delays_get_airport_status`.
2. List every active ground stop and GDP across the US (and every other active event) in one call → `faa_delays_list_active_events`.
3. See active en-route Airspace Flow Programs: which airspace, which flights, how much delay → `faa_delays_list_active_events` with `event_types: ["airspace_flow_program"]`.
4. Read the FAA's stated reason for each program (low ceilings, thunderstorms, runway construction, volume) → the `reason` field on every event.
5. Read the operations plan: which airports and routes the FAA expects to program later today, and how likely → `faa_delays_get_operations_plan`.
6. See an affected airport's current runway configuration and airport arrival rate → `faa_delays_get_airport_status` (`runwayConfiguration`).
7. Read the full advisory behind a program (program rate by hour, scope, delay assignment mode, comments), including past advisories → `faa_delays_get_advisory`.
8. Decode FAA traffic-management vocabulary (AAR, EDCT, FCA, ARTCC codes) → `faa_delays_list_reference`.

## Tools — detail

Shared conventions:

- **Airport directory.** A generated module built from FAA NASR `APT_BASE.csv`: one row per US 3-character location identifier (`COUNTRY_CODE = US`, every `ARPT_STATUS`), `{ faaId, icaoId?, name, city, state }` — 5,276 rows at the 2026-09-03 cycle, 2,597 of them with an ICAO code. It serves three purposes: the ICAO → FAA crosswalk the handler applies to each requested code, the membership check behind `unknown_airport`, and `airportName`/`city`/`state` for airports the feed does not list. Generation and refresh: Services.
- **Airport code input.** `AirportCode` = `z.preprocess(normalizeAirportCode, z.string().regex(/^[A-Z0-9]{3,4}$/))`. `normalizeAirportCode` trims and uppercases; non-string values pass through to the schema. The handler then resolves each code with `resolveAirportCode`: a 3-character code by FAA identifier, a 4-character code only when the directory lists it as the ICAO code of a US airport (`KSEA` → `SEA`, `PHNL` → `HNL`, `PANC` → `ANC`, `TJSJ` → `SJU`). The crosswalk is a lookup, never a prefix strip: a 4-character code the directory does not list that way (`K0S9`, `CYVR`, a private-strip identifier) fails the `unknown_airport` check with a typed recovery. A name (`Seattle`) fails the regex, a structural rejection carried by the framework's `invalid_arguments` hint. The `.describe()` states the accepted forms.
- **Advisory reference.** Every program with an advisory link carries `advisory: { number, date, url }`. `number` and `date` are parsed from the upstream link with `advn=(\d+)` and `adv_date=(\d{2})(\d{2})(\d{4})` (`advn=003&adv_date=09302026` → `3`, `2026-09-30`). The upstream link carries unencoded spaces in its `title` parameter, so it is never parsed with `new URL`, fetched, or returned. `url` is server-built: `https://www.fly.faa.gov/adv/adv_otherdis?advn={n}&adv_date={MMDDYYYY}`, the same URL `faa_delays_get_advisory` fetches. The reference is omitted when either field is absent from the link, or when the number falls outside the 1–999 that `faa_delays_get_advisory` accepts. `faa_delays_get_advisory` takes the pair as `advisory_number` and `date`, and the reference's `.describe()` states that mapping.
- **Upstream-authored text.** These fields are FAA-authored and rendered as data:
  - `faa_delays_get_airport_status`: `airportName`, `city`, `state`, every event's `reason`, `includedFacilities[]`, `includedFlights`, `controllingCenter`, `runwayConfiguration.arrivalRunways`/`departureRunways`, `closure.text`, `closureNotam.notamText`/`text`, `timezone`.
  - `faa_delays_list_active_events`: `location`, `locationName`, `reason`, `closureText`, and in `afp`: `constrainedArea.name`, `altitudeFloor`, `altitudeCeiling`, `departsFrom`, `arrivesTo`, `excludedDepartures`, `excludedArrivals`, `headingDirection`, `comments`.
  - `faa_delays_get_operations_plan`: planned `text`, `announcements[].text`.
  - `faa_delays_get_advisory`: `title`, `controlElement`, `subject`, `effectiveTime`, `sentAt`, `text`.
  - `faa_delays_list_reference`: pacing-airport `airportId` and `timezone`.

  `format()` flattens CR/LF/TAB to a single space in every inline slot (headings, bold labels, list items, table cells), removes every other C0 and C1 control and the bidi embedding, override, and isolate controls (U+202A–U+202E, U+2066–U+2069), and escapes `[`, `]`, `<`, and `>` so FAA text cannot form a link, image, autolink, or HTML tag; a backslash run directly before one of those is doubled, so the text cannot cancel the escape. Table cells escape every `\` and `|` as well. It renders free text (`closureNotam.notamText`, `closure.text`, AFP `comments`, operations-plan planned `text`, announcements) as a `>` blockquote with every line prefixed, and advisory `text` in a fenced `text` block whose fence is one backtick longer than the longest backtick run in the body. Notice fragments that interpolate an upstream value (an AFP name, a feed airport identifier) flatten it the same way. A value the FAA did not report is named or left out of the rendered line, never shown as a placeholder: a window with one bound reads `from X (end not reported)` or `until Y (start not reported)`, a delay band with one bound `at least N min` or `up to N min`, and GDP delay figures, coordinates, and AFP altitudes list only the parts present. `structuredContent` keeps every value verbatim.
- **`fetchedAt`** (output, every feed tool): when this server fetched the snapshot from the FAA. With the 60 s cache this can trail the call by up to a minute.
- **Error recoveries** name the calling tool. The feed reasons (`feed_unavailable`, `upstream_rate_limited`, `retry_deadline_exceeded`, `pacer_shed`, `feed_contract_changed`) are thrown by the service with `data.reason` and declared on every feed tool with `thrownBy: 'service'`; the framework fills the declared recovery onto the wire.

### `faa_delays_get_airport_status`

Description: "Get the current FAA traffic management status for one or more US airports: a headline status, every active event (ground stop, Ground Delay Program with its delay profile, arrival or departure delay, closure, deicing) with reason and times, and the runway configuration and airport arrival rate. Airports are FAA 3-character identifiers (SEA, ORD, JFK) or their ICAO codes (KSEA, PHNL); a code that names no US airport is rejected. The FAA feed lists only airports with an active event, so a known airport absent from it returns status no_active_events, and runway configuration is available only for listed airports."

| Param | Type | Maps to | Notes |
|:------|:-----|:--------|:------|
| `airports` | `z.preprocess(splitList, z.array(AirportCode).min(1).max(25))` | local filter over `/api/airport-events` | `splitList` turns a string into an array split on commas/whitespace (`"ORD, JFK"` → `["ORD","JFK"]`); arrays pass through. Either form is cut to 26 items before validation, so an oversized list fails `.max(25)` with at most 26 code issues (Design Decisions). Duplicates after normalization are dropped, keeping first order. One upstream fetch serves the whole batch. Describe: "1–25 US airports, each a 3-character FAA location identifier (SEA, ORD, 0S9) or its ICAO code (KSEA, PHNL, TJSJ), case-insensitive; a comma-separated string is also accepted. City and airport names are not accepted." |

Handler flow:

1. Resolve every normalized code in the airport directory, a 4-character code through the ICAO crosswalk. Any code not found fails the whole call with `ctx.fail('unknown_airport', …)` before any upstream request: the message names every unknown code, `data.unknownCodes` lists them, and a 4-character code is described as "not the ICAO code of a US airport with a 3-character FAA identifier" rather than as a missing identifier.
2. `Promise.allSettled([airportEvents, pacingAirports])`. A rejected `airport-events` leg is rethrown. A rejected `pacing-airports` leg is rethrown when `ctx.signal.aborted`; otherwise the pacing fields are omitted and a notice fragment is added.
3. Build one row per requested airport, in request order.

Output:

- `fetchedAt: string`
- `airports[]` in request order:
  - `airportId` (normalized FAA identifier), `requestedAs?` (the submitted ICAO code, present only when it differs from `airportId`; case and whitespace normalization alone does not set it)
  - `airportName` (feed `airportLongName` when listed, else the directory name), `city?`, `state?` (directory, present when NASR carries them). Echoing the resolved airport on every row lets a caller catch a valid code that names a different airport than intended.
  - `status: 'closed' | 'ground_stop' | 'ground_delay_program' | 'delays' | 'restrictions_only' | 'no_active_events'`. Precedence, first match wins: `airportClosure` → `closed`; `groundStop` → `ground_stop`; `groundDelay` → `ground_delay_program`; `arrivalDelay`/`departureDelay` → `delays`; listed with only `freeForm`, `deicing`, or `airportConfig` → `restrictions_only`; absent from the feed → `no_active_events`. The `.describe()` states this rule.
  - `listedInFeed: boolean`, `latitude?`, `longitude?` (listed only; numbers parsed from upstream strings, omitted if unparseable)
  - `isPacingAirport?: boolean`, `timezone?`, from `/api/pacing-airports`. Omitted when that leg failed.
  - `runwayConfiguration?: { arrivalRunways?, departureRunways?, arrivalRatePerHour?, reportedAt? }` ← `airportConfig.{arrivalRunwayConfig, departureRunwayConfig, arrivalRate, sourceTimeStamp}`; the runway strings are trimmed (the feed pads some, `" 25L/24R"` live)
  - `groundStop?: { reason?, startTime?, endTime?, probabilityOfExtension?: 'low'|'medium'|'high', includedFacilities?: string[], updatedAt?, advisory?, includedFlights?, controllingCenter? }`. The last two are read when present; the dashboard reads them on `groundDelay` but not on `groundStop`, so they are unconfirmed there.
  - `groundDelayProgram?: { reason?, averageDelayMinutes?, maximumDelayMinutes?, startTime?, endTime?, updatedAt?, controllingCenter?, departureScopeNm?, includedFacilities?: string[], includedFlights?, delayProfile?: { startTime, intervalMinutes: 15, averageDelayMinutes: number[] }, advisory? }`
  - `arrivalDelay?` / `departureDelay?`: `{ reason?, minMinutes?, maxMinutes?, trend?: 'increasing'|'decreasing', updatedAt? }`
  - `closure?: { text?, startTime?, endTime?, updatedAt? }` ← `airportClosure`. The airport is closed to all operations; `text` lists exceptions.
  - `closureNotam?: { notamText?, text?, notamNumber?, issuedAt?, startTime?, endTime?, updatedAt? }` ← `freeForm`, a NOTAM-worded closure or restriction ("closed to non-scheduled transient GA").
  - `deicing?: { startedAt? }` ← `deicing.eventTime`

Field derivations (verified or bundle-derived; see API Reference):

- `includedFacilities`: departure facilities in scope. ARTCC codes for a tier-scoped program (`ZAU ZDC …`, seen in a ground-stop advisory), ICAO airports for named extra facilities (`CYVR …`, seen live on a GDP). The describe says both.
- `includedFlights`: upstream `": ALL CONTIGUOUS US DEP"`, with the leading `": "` stripped.
- `controllingCenter` ← `groundDelay.center` (the controlling ARTCC).
- `departureScopeNm` ← `groundDelay.departureScope` (the advisory's `DEP SCOPE`, a distance in nautical miles).
- `delayProfile` ← `groundDelay.fuelFlowAdvisoryDelayTime`: `startTime` from its `startTime`, `averageDelayMinutes` from `dasDelays.dasDelay[]` ordered by `seq`. Each value is the average delay for one 15-minute arrival interval (confirmed from the dashboard's "Delay Trend" table code, and by count: a 01:00–05:59Z program carried 20 values).
- `minMinutes`/`maxMinutes` ← `arrivalDeparture.min`/`max` (`"16 minutes"` live; the hour form `"1 hour and 57 minutes"` appears in the legacy XML and is accepted too), parsed by `(?<!\d)(\d{1,4})\s*hours?` + `(?<!\d)(\d{1,4})\s*minutes?`, so a count longer than four digits reads as absent. If `arrivalDeparture` is absent, derive the band from `averageDelay` + `trend` by the FAA's documented rule: increasing → `min = avg+1, max = avg+15`; decreasing → `min = avg-14, max = avg`. `averageDelay` itself is not surfaced (Design Decisions).
- `probabilityOfExtension` ← `groundStop.probabilityOfExtension` (`LOW`/`MEDIUM`/`HIGH`, lowercased). Describe: "low <30 %, medium 30–60 %, high >60 % per the FAA."

Enrichment: `notice?: string` (kind `notice`), one `ctx.enrich.notice()` call with the fragments below joined:

- Every requested airport is `no_active_events`: "None of the requested airports has an active FAA traffic management event. faa_delays_get_operations_plan lists programs the FAA expects later today."
- An arrival/departure delay's `updatedAt` is more than 6 h older than `fetchedAt`: "`SEA` departure delay was last updated `N` h ago; the FAA feed can keep a delay entry after it lapses."
- The pacing-airport leg failed: "Pacing-airport flags and time zones are omitted because that FAA list could not be fetched."
- Feed rows were skipped by the parser: "`N` FAA feed rows could not be read and were skipped." (singular for one row: "1 FAA feed row could not be read and was skipped.")

The stale-delay and skipped-rows fragments come from `src/mcp-server/tools/notices.ts`, shared with the other feed tools so the wording matches.

Errors:

| reason | code | when | recovery |
|:-------|:-----|:-----|:---------|
| `unknown_airport` | `NotFound` (`severity: 'notice'`) | A requested code is not a 3-character identifier in the FAA NASR airport directory, or a 4-character code that is not the ICAO code of one | "Send each airport as its 3-character FAA identifier (SEA) or ICAO code (KSEA); faa_delays_list_reference topic identifiers explains the accepted forms and topic pacing_airports lists the FAA major airports." |
| `feed_unavailable` | `ServiceUnavailable` (retryable, `thrownBy: 'service'`) | NAS Status unreachable, 5xx, an attempt timeout, or an HTML maintenance page, after retries | "The FAA NAS Status feed is temporarily unreachable; call faa_delays_get_airport_status again in about a minute." |
| `upstream_rate_limited` | `RateLimited` (retryable, `thrownBy: 'service'`) | FAA returned 429 after retries (`retryAfter` is set only when the FAA sends `Retry-After`), or the pacer shed a call while an FAA 429 held its cooldown gate closed (`retryAfter` is then when this server next sends to the FAA) | "The FAA feed is limiting request rate; wait the retryAfter interval in this error's data (about a minute when it carries none), then call faa_delays_get_airport_status again." |
| `retry_deadline_exceeded` | `Timeout` (retryable, `thrownBy: 'service'`) | The 20 s retry budget ran out (the `withRetry` deadline's own reason) | "The FAA NAS Status feed is responding slowly; call faa_delays_get_airport_status again in about a minute." |
| `pacer_shed` | `RateLimited` (retryable, `thrownBy: 'service'`) | This server's own queue to the FAA would wait past 10 s with no FAA 429 holding the cooldown gate (the pacer's own reason, carrying `retryAfter`) | "This server is pacing its requests to the FAA; wait the retryAfter seconds in this error's data, then call faa_delays_get_airport_status again." |
| `feed_contract_changed` | `SerializationError` (not retryable, `thrownBy: 'service'`) | The feed path returned 404/410, or a body whose shape this server no longer recognizes | "The FAA NAS Status feed is not serving the format this server reads, which usually means the FAA changed it, so an immediate retry will not help; faa_delays_get_advisory still reads ATCSCC advisories, numbered from 1 each UTC day, so today's program advisories can be read by advisory_number with today's UTC date." |

### `faa_delays_list_active_events`

Description: "List every active FAA traffic management event across the National Airspace System in one call: ground stops, Ground Delay Programs, Airspace Flow Programs, arrival and departure delays, airport closures, closure NOTAMs, and deicing. Rows are sorted by severity (closures, ground stops, then GDPs and then AFPs each by average delay, arrival/departure delays by band maximum, closure NOTAMs, deicing) and carry the reason, delay figures, times, and an advisory reference for faa_delays_get_advisory. Use faa_delays_get_airport_status for the full detail of one airport, including its GDP delay profile and runway configuration."

| Param | Type | Maps to | Notes |
|:------|:-----|:--------|:------|
| `event_types` | `z.preprocess(normalizeEventTypes, z.array(EventType).optional())` | local filter | `EventType` = `ground_stop \| ground_delay_program \| airspace_flow_program \| arrival_delay \| departure_delay \| airport_closure \| closure_notam \| deicing`. `normalizeEventTypes`: a string naming no types (blank, or only commas) or an empty array → `undefined`; a string is split on commas first, and a piece that normalizes to one type or alias stays whole (`"departure delay, arrival delay"`) while any other piece is split on whitespace (`"gs gdp"`); values are trimmed, lowercased, `-`/space → `_`; aliases `gs` → `ground_stop`, `gdp` → `ground_delay_program`, `afp` → `airspace_flow_program`. The normalized list is deduped, then cut to 9 entries (one past the type count), which never changes whether it validates. Anything else reaches the enum and fails with the framework's hint listing the options. Omitted → all types. |

Upstream: `Promise.allSettled([airportEvents, enrouteEvents])`.

- A rejected `airport-events` leg is rethrown: the call fails.
- A rejected `enroute-events` leg is rethrown when `ctx.signal.aborted`, or when the applied filter is exactly `["airspace_flow_program"]` (nothing else was asked for). Otherwise the call degrades: AFP rows are omitted, `enRouteFeed` reports why (`format_changed` when the leg's reason is `feed_contract_changed`, else `unavailable`), `countsByType.airspace_flow_program` is omitted, and a notice fragment says so.

Output:

- `fetchedAt: string`
- `events[]`, each a flat object:
  - `eventType`, `location` (FAA airport ID, or the AFP name for `airspace_flow_program`), `locationName?` (airport long name)
  - `reason?`, `averageDelayMinutes?` (GDP, AFP), `maximumDelayMinutes?` (GDP), `delayRangeMinutes?: { min?, max? }` (arrival/departure delay; a bound the FAA did not report is absent, and the band is absent when it reported neither), `trend?`, `probabilityOfExtension?` (ground stop)
  - `startTime?`, `endTime?`, `updatedAt?`
  - `closureText?` (`airport_closure` text, or `closure_notam` NOTAM text)
  - `advisory?`
  - `afp?` (only on `airspace_flow_program`): `{ constrainedArea: { type: 'airport'|'artcc'|'sector'|'tracon'|'special_use_airspace'|'fix'|'fca', name? }, altitudeFloor?, altitudeCeiling?, departsFrom?, arrivesTo?, excludedDepartures?, excludedArrivals?, headingDirection?, filtersMatchAny?, comments?, delayProfile? }`
- Airport rows reuse the `faa_delays_get_airport_status` derivations: `reason`, the delay band, the advisory ref, and `closureText` (`airportClosure.text` or `freeForm.simpleText`). AFP rows map as follows: `location` ← `airspaceFlowProgram.afpName`; `reason` ← `airspaceFlowProgram.impactingCondition`; `averageDelayMinutes` ← `airspaceFlowProgram.avgDelay`; `startTime`/`endTime`/`updatedAt` ← `airspaceFlowProgram.{startTime,endTime,updatedAt}`; `advisory` ← the row-level `advisoryUrl`. Inside `afp`: `altitudeFloor`/`altitudeCeiling` ← `airspaceFlowProgram.lowerAltitude`/`upperAltitude` (strings, passed through); `delayProfile` ← `airspaceFlowProgram.fuelFlowAdvisoryDelayTime` (same derivation as the GDP); row-level `departsAny` → `departsFrom`, `arrivesAny` → `arrivesTo`, `departsNone` → `excludedDepartures`, `arrivesNone` → `excludedArrivals`, `fcaHeadingDirection` → `headingDirection`, `isAnyConditions` → `filtersMatchAny` (true: departs OR arrives filters apply; false: AND), `comments` → `comments`. `constrainedArea` is resolved per API Reference.
- Sort, stated in the describe: `airport_closure`, `ground_stop`, `ground_delay_program` (by `averageDelayMinutes` desc), `airspace_flow_program` (by `averageDelayMinutes` desc), `arrival_delay`/`departure_delay` (by `delayRangeMinutes.max` desc, or `min` when only that bound is reported), `closure_notam`, `deicing`. Within a type, rows that report no delay figure follow those that do; ties by `location`.

Enrichment. The required fields are written in one `ctx.enrich({ … })` call right after both legs settle, before the filter and sort branches. `ctx.enrich.total()` and `ctx.enrich.echo()` write the fixed keys `totalCount` and `effectiveQuery`, so these fields go through `ctx.enrich({ … })` with `enrichmentTrailer` labels and renders instead of those helpers.

| Field | Trailer | Value |
|:------|:--------|:------|
| `totalActive: number` | label "Total active" | Every active event read, before `event_types`; excludes AFPs when `enRouteFeed` is not `ok` |
| `shown: number` | label "Shown" | Count after filtering |
| `countsByType: { ground_stop, ground_delay_program, airspace_flow_program?, arrival_delay, departure_delay, airport_closure, closure_notam, deicing }` (integers, zeros included) | render: `**By type:** ground_stop 1 · ground_delay_program 2 · …` (non-zero types, "none" when all zero, "airspace_flow_program unknown" when absent) | Counted over the whole feed before the filter. Describe: "Active events per type across the whole feed, counted before the event_types filter so types the filter excluded stay visible. airspace_flow_program is absent when the en-route feed could not be read." A `z.object` rather than `z.record(EventType, …)`, which Zod 4 treats as exhaustive and which says nothing per key. |
| `appliedEventTypes: EventType[]` | render: `**Event types:** ground_stop, …` or "all" | The normalized filter, or every type when omitted |
| `enRouteFeed: 'ok' \| 'unavailable' \| 'format_changed'` | label "En-route feed" | Whether AFPs were read |
| `notice?: string` | kind `notice` | The fragments below, composed into one string |

Notice fragments:

- `enRouteFeed: 'unavailable'`: "The FAA en-route feed could not be read, so Airspace Flow Programs are missing from this list and from countsByType; call faa_delays_list_active_events again in about a minute for them."
- `enRouteFeed: 'format_changed'`: "The FAA en-route feed returned a format this server does not read, so Airspace Flow Programs are missing from this list; airport events are complete, and faa_delays_get_operations_plan names the en-route initiatives the FAA plans."
- Filtered, `shown = 0`, `totalActive > 0`: "No active `ground_stop` events; `N` other events are active (see countsByType) — call faa_delays_list_active_events without event_types to see them."
- `totalActive = 0` and `enRouteFeed: 'ok'`: "The FAA reports no active traffic management events nationwide. Call faa_delays_get_operations_plan for programs expected later today."
- Filter includes `airspace_flow_program`, none active, `enRouteFeed: 'ok'`: "No Airspace Flow Programs are active; en-route constraints the FAA expects later are in faa_delays_get_operations_plan."
- A returned `arrival_delay`/`departure_delay` row's `updatedAt` is more than 6 h older than `fetchedAt`, one fragment per row in sort order, the same wording as `faa_delays_get_airport_status`: "`ORD` departure delay was last updated `N` h ago; the FAA feed can keep a delay entry after it lapses." Rows the `event_types` filter excluded are not checked.
- Feed rows were skipped: "`N` FAA feed rows could not be read and were skipped." (singular for one row)

Errors: the five feed reasons from `faa_delays_get_airport_status` (not `unknown_airport`), with the recovery tool name changed to `faa_delays_list_active_events`.

### `faa_delays_get_operations_plan`

Description: "Get the FAA Command Center's current operations plan: terminal programs (possible ground stops and delay programs by airport) and en-route initiatives (route closures, severe-weather avoidance plans) expected later in the day, each with its planned UTC time and stated likelihood, plus current ATCSCC announcements. The advisory reference opens the full plan text with faa_delays_get_advisory, including active constraints and runway closures this summary omits."

No input (empty `z.object({})`).

Upstream: `Promise.allSettled([operationsPlan, miscellaneousInfo])`. A rejected `operations-plan` leg is rethrown. A rejected `miscellaneous-info` leg is rethrown when `ctx.signal.aborted`; otherwise `announcements` is omitted and a notice fragment is added.

Output:

- `fetchedAt: string`
- `advisory?` (parsed from `link`)
- `terminalPlanned[]`, `enRoutePlanned[]`, each `{ text, timeQualifier?: 'after'|'until'|'by'|'between', timeUtc?: string, likelihood?: 'possible'|'probable'|'expected' }`:
  - `text` ← `event` with tabs → a single space and a leading `-` stripped from the description.
  - Parse `^(AFTER|UNTIL|BY|BETWEEN)\s+(\d{4})` for qualifier and `HHMM`. If upstream `time` is non-empty, it wins over the parse for `timeUtc`. For `between`, `timeUtc` is the start of the window and the end stays in `text`; the `timeQualifier` describe says so.
  - `timeUtc` carries no date and is never anchored to one. Its day is the plan's event window, the `EVENT TIME` line of the plan advisory, which can start on the UTC day after the advisory date (a plan issued 2026-09-30 read "EVENT TIME: 01/0000 - AND LATER", so its `AFTER 1200` meant 2026-10-01T12:00Z). The `timeUtc` describe says so and points at `faa_delays_get_advisory`.
  - `likelihood` is the last word of `text` when it is `POSSIBLE`, `PROBABLE`, or `EXPECTED`. The describe cites the FAA's meanings: possible <30 %, probable 30–60 %, expected "most likely".
- `announcements?: { text }[]` ← `miscellaneous-info[].event`. `[]` when there are none; absent when that list could not be read.

Enrichment: `notice?`, fragments joined:

- Both planned lists empty: "The operations plan lists no planned programs. faa_delays_list_active_events shows what is active now."
- `advisory` absent: "The feed carried no advisory link for this plan."
- Announcements leg failed: "ATCSCC announcements are omitted because that FAA list could not be read; the operations plan above is complete."
- Feed rows were skipped by the parser (plan and announcements combined): "`N` FAA feed rows could not be read and were skipped." (singular for one row)

Errors: the five feed reasons, recovery naming `faa_delays_get_operations_plan`; the `feed_contract_changed` recovery points at today's operations plan advisory, found by `advisory_number` with today's UTC date.

### `faa_delays_get_advisory`

Description: "Get the full text of one ATCSCC advisory by its number and UTC date, read from the advisory reference that faa_delays_list_active_events and faa_delays_get_airport_status return on program rows and faa_delays_get_operations_plan returns for the plan. Advisory text carries what the status feed omits: program rate by hour, delay assignment mode, scope, comments, and the operations plan's active constraints and runway closures. Advisory numbers restart at 1 each UTC day, and older advisories remain available."

| Param | Type | Maps to | Notes |
|:------|:-----|:--------|:------|
| `advisory_number` | `z.preprocess(stripAdvzy, z.number().int().min(1).max(999))` | `advn` | `stripAdvzy`: a string has a leading `ADVZY` (any case) removed, is trimmed, then must be all digits to become a number (`"082"`, `"ADVZY 082"` → `82`). Anything else passes through and fails the schema. The describe names the three tools whose advisory reference supplies it. `inputAliases: { number: 'advisory_number' }` accepts the reference's own field name. |
| `date` | `z.preprocess(normalizeDate, z.iso.date({ abort: true, error }).refine(notAfterTomorrow))` | `adv_date` (`MMDDYYYY`) | UTC advisory date, `YYYY-MM-DD`. `normalizeDate` trims and rewrites `MM/DD/YYYY`, the form printed in advisory titles, or its unpadded `M/D/YYYY`, to `YYYY-MM-DD`; anything else passes through to `z.iso.date()`, which rejects impossible dates with a message naming the three accepted forms. A date later than tomorrow's UTC date is rejected before any request (Design Decisions); `abort` keeps a malformed date to its one issue. Validation matters because the upstream answers a malformed `adv_date` with the same 200 page as a missing advisory. |

Upstream: `GET https://www.fly.faa.gov/adv/adv_otherdis?advn={n}&adv_date={MMDDYYYY}` (https, no `.jsp`, so there is no redirect; the other title/facility query params are cosmetic and omitted). Parsing:

- `text` ← HTML-entity-decoded content of the single `<PRE>…</PRE>` block, trimmed (bodies end in a literal `&nbsp;`).
- `title` ← the `<TH class=header …>` cell, `&nbsp;` → space. Title parse `^ATCSCC ADVZY (\d+) (\S+) (\d{2}/\d{2}/\d{4}) (.+)$` → `controlElement` (`SEA/ZSE`, `DCC`), `subject` (`CDM GROUND DELAY PROGRAM`). A title that doesn't match (for example a Canadian advisory) leaves those two absent.
- `effectiveTime?` and `sentAt?` ← the `TD class=val` cell after the `EFFECTIVE TIME:` and `SIGNATURE:` label cells, entity-decoded and trimmed, raw (`DDHHMM-DDHHMM`, `YY/MM/DD HH:MM`), when present.
- Each element is found by its opening tag, then the next `</PRE>`, `</TH>`, or `</TD>` from there; tags are stripped from a cell with `<[^<>]*>`. Every search runs in time linear in the page.
- Entities: `&nbsp;`, `&amp;`, `&lt;`, `&gt;`, `&quot;`, `&apos;`, and decimal or hex numeric entities. A numeric entity naming a control character other than TAB, LF, or CR, or a bidi control (U+202A–U+202E, U+2066–U+2069), stays encoded.

Outcomes:

- No `<PRE>` block, no title, and the database's `NO Advisory.` marker → the miss result `{ found: false, advisoryNumber, date, url, guidance }`, with guidance: "No ATCSCC advisory `NNN` exists for `YYYY-MM-DD` (UTC). Take the number and date from an advisory reference on faa_delays_list_active_events, faa_delays_get_airport_status, or faa_delays_get_operations_plan; numbers restart at 1 each UTC day."
- Title present but no `<PRE>` → `advisory_contract_changed`.
- No `<PRE>`, no title, and no marker (an error or maintenance page) → `advisory_service_unavailable`.

Output: `found: boolean`, `advisoryNumber`, `date`, `url`, `title?`, `controlElement?`, `subject?`, `effectiveTime?`, `sentAt?`, `text?`, `guidance?`.

Enrichment, all optional and written only when the text exceeds a fixed 50,000-character ceiling (above every probed advisory, no caller param): `ctx.enrich.truncated({ shown: 50_000, cap: 50_000, guidance })` writes `truncated`, `shown`, `cap`, and `notice` (guidance: "Advisory text was cut at 50,000 of `N` characters; the full advisory is at the url field."), and `ctx.enrich({ totalChars })` adds the full length. Fields: `truncated?: boolean`, `shown?: number`, `cap?: number`, `totalChars?: number`, `notice?: string`. No required fields, so no path can skip one.

Errors:

| reason | code | when | recovery |
|:-------|:-----|:-----|:---------|
| `advisory_service_unavailable` | `ServiceUnavailable` (retryable, `thrownBy: 'service'`) | FAA advisories database unreachable, 5xx, an attempt timeout, or an error page, after retries | "The FAA advisories database is temporarily unreachable; call faa_delays_get_advisory again in about a minute." |
| `upstream_rate_limited` | `RateLimited` (retryable, `thrownBy: 'service'`) | 429 from the advisories host after retries, or a shed while such a 429 holds the cooldown gate closed | "The FAA advisories database is limiting request rate; wait the retryAfter interval in this error's data (about a minute when it carries none), then call faa_delays_get_advisory again." |
| `retry_deadline_exceeded` | `Timeout` (retryable, `thrownBy: 'service'`) | The 20 s retry budget ran out | "The FAA advisories database is responding slowly; call faa_delays_get_advisory again in about a minute." |
| `pacer_shed` | `RateLimited` (retryable, `thrownBy: 'service'`) | This server's queue to the advisories host would wait past 10 s with no 429 holding the cooldown gate | "This server is pacing its requests to the FAA; wait the retryAfter seconds in this error's data, then call faa_delays_get_advisory again." |
| `advisory_contract_changed` | `SerializationError` (not retryable, `thrownBy: 'service'`) | Advisory page found (title present) but its text block is missing, or the path returned 404/410 | "The FAA changed the advisory page layout, so retrying will not help; faa_delays_get_airport_status and faa_delays_list_active_events still report each program's reason, times, and delays, and the advisory opens in a browser at the url in this error's data." |

`advisory_contract_changed` carries `data.url`, server-built from validated inputs, so it is safe to expose.

## Services

| Service | Wraps | Used By |
|:--------|:------|:--------|
| `NasStatusService` | `https://nasstatus.faa.gov/api/{airport-events, enroute-events, operations-plan, miscellaneous-info, pacing-airports}` | `get_airport_status`, `list_active_events`, `get_operations_plan`, `list_reference` |
| `AdvisoryService` | `https://www.fly.faa.gov/adv/adv_otherdis` | `get_advisory` |
| Airport directory (static module, no init) | Generated from FAA NASR `APT_BASE.csv` | `AirportCode` normalization, `get_airport_status`, `list_reference` (`identifiers`) |

**Airport directory.** `src/services/airport-directory/nasr-airports.generated.ts` exports the NASR effective date and one TSV string (`faaId\ticaoId\tname\tcity\tstate` per line, ~210 KB raw, ~81 KB gzipped); `airport-directory.ts` parses it once, on first use, into two `Map`s (by FAA identifier, by ICAO code). `scripts/refresh-airport-directory.ts` (package script `refresh:airports`) regenerates the module: it reads the NASR subscription index, picks the newest cycle whose effective date is on or before today (the index lists the next cycle before it takes effect), downloads that cycle's `{DD_Mon_YYYY}_APT_CSV.zip` with GET (the host answers HEAD with 503), extracts `APT_BASE.csv` with the system `unzip`, reads it as latin-1, keeps rows with `COUNTRY_CODE = US` and a 3-character `ARPT_ID`, and writes the module sorted by identifier. `--zip <path>` reads an already-downloaded archive instead of the live index. It runs at maintenance releases, never at runtime or in tests, and refuses to write a table smaller than 5,000 rows, one missing any pacing airport (the list is fetched live from `/api/pacing-airports`), one whose ICAO codes repeat or collide with a 3-character identifier, or one carrying more than one `EFF_DATE`, so a truncated or mixed download fails loudly.

**Fetch boundary (both HTTP services): plain `fetch` with an accept-list of `200` only, not `fetchWithTimeout`.** A 404 on a known feed path means the contract changed, not "entity not found" (`fetchWithTimeout` would throw `NotFound`). A 200 can carry an HTML maintenance page, and a missing advisory is a 200 the parser reads as a miss. So each service classifies statuses itself:

| Response | Classification |
|:---------|:---------------|
| 200 + `application/json` (feeds) / `text/html` (advisories) | Parse |
| 200 + `text/html` on a feed | `feed_unavailable` (`ServiceUnavailable`, transient) — maintenance page |
| 200 + a feed body that is not valid JSON | `feed_unavailable` (`ServiceUnavailable`, transient) — a truncated or interrupted transfer |
| 200 + a body over the host's ceiling (4 MiB feeds, 2 MiB advisories, counted after gzip decoding) | `feed_unavailable` / `advisory_service_unavailable` (`ServiceUnavailable`, transient); the read stops at the ceiling and the rest is cancelled unread |
| 404, 410 | `feed_contract_changed` / `advisory_contract_changed` (`SerializationError`, `retryable: false`) |
| 429 | `httpErrorFromResponse(res, { service, captureBody: false, data: { reason: 'upstream_rate_limited' } })` → `RateLimited` with `retryAfter` |
| other non-2xx | `httpErrorFromResponse(res, { service, captureBody: false, data: { reason: 'feed_unavailable' } })` (or `advisory_service_unavailable`) |
| network error | `serviceUnavailable` carrying the same reason; the message names only the service ("… is unreachable."), and the runtime error text stays on `{ cause }`, which reaches the log record but not the caller |
| this service's per-attempt timer fired | `timeout(…)` carrying the same reason (transient, retried) |

`captureBody: false` keeps the 49 KB HTML error page out of `error.data`. The per-attempt timeout is an `AbortController` + `setTimeout` (not `AbortSignal.timeout()`, which the framework avoids for a Bun realm mismatch) combined with the attempt signal through `AbortSignal.any`, armed across the header phase and the body read, and cleared in `finally`. The body is read as a stream and decoded as UTF-8 chunk by chunk, so the size ceiling is checked before the whole body is held. Requests send `Accept-Encoding: gzip` (verified supported) and a `User-Agent` of `faa-traffic-delays-mcp-server/<version>`; the advisories host sets a `JSESSIONID` cookie, which is ignored.

**Resilience:**

- Retry: `withRetry` around fetch + parse, `{ maxRetries: 2, baseDelayMs: 500, deadlineMs: 20_000, operation }`. `operation` is caller-readable, since `withRetry` puts it in the deadline message and in `data.operation` on exhaustion: `The FAA NAS Status <label> feed` (labels `airport events`, `en-route events`, `operations plan`, `announcements`, `pacing airports`) or `The FAA advisories database`. The log record's own `RequestContext.operation` keeps the code name (`NasStatusService.airport-events`, `AdvisoryService.getAdvisory`). Each attempt receives `{ signal, remainingMs }` and runs `pacer.run(() => fetchAndParse(signal, Math.min(8_000, remainingMs)), { signal, maxWaitMs: Math.min(10_000, remainingMs) })`: retry outside, pacer inside, so each attempt re-queues. A parallel pair runs two ladders concurrently, so wall-clock stays under 20 s, inside a 60 s client timeout. `feed_contract_changed` carries `retryable: false` and fails fast. Deadline expiry rejects as `Timeout` with `data.reason: 'retry_deadline_exceeded'`; a shed rejects as `RateLimited` with `data.reason: 'pacer_shed'` and `retryAfter`, which `withRetry` does not retry. Both reasons are declared on every calling tool. A shed while the pacer's cooldown gate is closed (`pacer.cooldown.remainingMs > 0`) is rethrown as `upstream_rate_limited`, keeping the shed's `retryAfter` and the shed as `cause`: only an upstream 429 closes that gate, and a tool's parallel legs escalate it together, so their retries are shed rather than refused by the FAA.
- Pacing: one `createPacer` per host. `nasstatus`: `{ name: 'FAA NAS Status', limits: [{ requests: 30, perMs: 60_000 }], maxConcurrent: 4, cooldown: { baseMs: 5_000, maxMs: 60_000 } }`. `fly.faa.gov`: `{ name: 'FAA advisories database', limits: [{ requests: 20, perMs: 60_000 }], minStartGapMs: 500, maxConcurrent: 2, cooldown: { baseMs: 5_000, maxMs: 60_000 } }`. The name reaches the shed message ("No FAA NAS Status request slot available within the caller's wait budget.") as well as the `mcp.pacer.name` metric attribute, so it is written as words. `maxWaitMs` is a `pacer.run` option, passed per attempt as above. Sizing: no published limit, so the ceilings approximate a few dashboard tabs; with caching and single-flight, real feed volume is ≤ 5 requests/min. Pacers are `dispose()`d in `createApp({ teardown })`.
- Cache: an in-process, per-endpoint cache (not `ctx.state` — public data identical for every tenant) with single-flight, so concurrent callers share one in-flight request. TTLs: feeds 60 s, `pacing-airports` 6 h, advisory text 6 h (an issued advisory number is immutable), advisory miss 6 h once its UTC date has been over for an hour (no advisory can join it) and 60 s before that (the next number may appear), LRU cap 200 advisories. An expired entry is never served when the refresh fails: the error surfaces.
- Cancellation under single-flight: the shared ladder runs under its own deadline and is never given a caller's `ctx.signal`, because it serves every caller waiting on it. Each caller awaits the shared promise raced against its own `ctx.signal`; a cancelled caller rejects alone (the handler factory reports `RequestCancelled`), while the fetch completes and fills the cache for the rest.

**Tolerant parsing (`NasStatusService`):** each feed body is `unknown`, read field by field with type guards, never through a strict Zod parse of the whole body.

- Top-level shape wrong (`airport-events`/`enroute-events`/`pacing-airports`/`miscellaneous-info` not an array; `operations-plan` not an object with at least one of `link`/`terminalPlanned`/`enRoutePlanned`) → `feed_contract_changed`. Its message names the feed by the same label as the retry and malformed-JSON messages ("The FAA NAS Status operations plan feed returned a shape this server does not recognize (…)."); `data.feed` keeps the path segment.
- An empty array is the normal quiet state for every array feed (`enroute-events` returned `[]` at every probe) and never a drift signal.
- Row key missing (`airportId` non-empty string; `airspaceFlowProgram.afpName` non-empty string; pacing `airportId`) → the row is skipped and counted. If every row of a non-empty array is skipped → `feed_contract_changed`. On the en-route leg that error degrades `faa_delays_list_active_events` rather than failing it.
- A known field with an unexpected type is omitted from output (never coerced), and the drift is logged once per field per process at `warning` with field path and observed type. Every drift and skipped-row detail rides the log record's `extra` (`withExtra`), because the framework logger keeps only the canonical context keys plus `extra`.
- Unknown row keys (a new event type) are logged at `warning` once per key per process and otherwise ignored.
- Drift logging keeps at most 256 distinct signals per process and logs an unknown key by its first 64 characters, because both come from the upstream body.
- A number the output cannot carry is omitted, never surfaced: a non-finite JSON number (`1e999`) is drift like any wrong-typed field (in a delay profile entry it drops the profile), a delay-band duration whose count runs past four digits reads as absent, and an `averageDelay` too long to represent is left out like any unreadable string.
- Skipped rows are logged at `warning` and surfaced in the tool's `notice`, because a missing row changes the national picture.

**Test boundary.** Both HTTP services take `{ fetch?: typeof fetch; now?: () => number; userAgent?: string }` through their constructor (defaults `globalThis.fetch`, `Date.now`, a bare `faa-traffic-delays-mcp-server`). `init*Service(options)` runs in `setup()`, which passes `userAgent` with the server version, and tests construct services directly. There are no env vars for seams. Fixtures: the captured probe bodies (`airport-events` with GDP/departure delay/NOTAM closure/config rows, `operations-plan`, `miscellaneous-info`, `pacing-airports`, one GDP and one operations-plan advisory page, a missing-advisory page, the 404 HTML page), all with synthetic values, plus a synthetic `enroute-events` row built to the bundle-derived shape (API Reference). Tests drive `createFetchMock`, and the clock seam covers cache expiry and staleness notices. The airport directory is the real generated module.

**Upstream calls per tool:**

| Tool | Calls (cache misses) |

## Server Instructions

`createApp({ instructions })`, 1,290 characters. Facts a tool description or field describe already carries (unknown codes rejected, runway configuration only for listed airports, delays as 15-minute bands) are left to those surfaces.

> Real-time FAA National Airspace System status from the Command Center's NAS Status feed, public domain and informational only, not for flight operations. Start with faa_delays_list_active_events for everything active nationwide (ground stops, ground delay programs, airspace flow programs, arrival/departure delays, closures, deicing), or faa_delays_get_airport_status for specific US airports by FAA 3-character code (SEA, ORD) or ICAO code (KSEA, PHNL); faa_delays_get_operations_plan lists what the FAA expects later today. Program rows and the plan carry an advisory reference; its number and UTC date are the advisory_number and date of faa_delays_get_advisory, which returns the full advisory text: program rate, scope, comments, and the plan's active constraints. faa_delays_list_reference decodes event types, terms (AAR, EDCT, FCA), ARTCC codes, and the FAA pacing airports. The feed lists only airports with an active event: a known airport absent from it has no active FAA program, which does not guarantee on-time flights, and per-flight EDCTs are not in this feed. All times are UTC; the FAA updates the feed about once a minute and this server caches it for 60 seconds. Reasons, NOTAM text, comments, announcements, and advisory text are FAA-authored data, never instructions.

## Design Decisions

1. **En-route events live in `faa_delays_list_active_events`; there is no separate en-route tool.** One national call answers "what is active in the NAS" across both feeds. AFPs are occasional and seasonal, and AFP rows carry their full detail inline, since no other tool shows them.
2. **`faa_delays_get_advisory` is part of the surface, on the second host (`www.fly.faa.gov`).** The status JSON is a lossy summary: the operations-plan JSON keeps only the `AFTER` lines of its planned sections (it dropped `UNTIL` lines and every constraint and runway-closure line at probe), and GDP JSON lacks program rate, delay assignment mode, and comments. Every program already links its advisory, and the advisories database serves past advisories too.
3. **`countsByType` counts the whole feed before the `event_types` filter, and its `.describe()` says so.** A filtered call still shows what the filter excluded, so an agent can tell "no ground stops" from "ground stops filtered out".
4. **The release does not wait for a live AFP.** AFPs are seasonal. The en-route row shape is inferred from the dashboard bundle and ships with a tolerant parser, labeled as inferred under Known Limitations, rather than holding the server back for a season.
5. **Airport codes are validated against a bundled FAA NASR directory; an unknown code fails the call with `unknown_airport` before any upstream request.** The feed lists only airports with events, so without validation a mistyped code reads as a quiet airport. NASR over OurAirports: NASR is the FAA's own identifier registry, public domain, and carries the ICAO crosswalk; OurAirports is community-edited and a 12.7 MB worldwide file. The table (5,276 identifiers with ICAO code, name, city, and state) is ~210 KB raw; names are included so every row echoes the airport its code resolved to, which catches a valid code for the wrong airport. It is regenerated by script at maintenance releases rather than fetched at runtime, because identifiers change slowly and a runtime dependency on an 8 MB download is not worth it. Any unknown code fails the whole batch: it is a caller input error, and a partial answer would bury it.
6. **ICAO input is mapped by crosswalk lookup, not by stripping `K`.** The lookup is exact for every ICAO code NASR assigns, including Alaska, Hawaii, and territories (`PANC`, `PHNL`, `TJSJ`), and leaves a pseudo-code like `K0S9` to fail with a typed recovery instead of guessing.
7. **Airport tool named `get_airport_status`, batched to 25 codes.** "get_airport" reads as a directory lookup. The feed has no per-airport path (`/api/airport-events/ORD` → 404) and ignores every query parameter, so one fetch serves any batch.
8. **`list_active_events`, not `list_active_programs`.** The rows include delays, closures, and deicing, which are not programs. "Events" is the FAA dashboard's own term ("Active Airport Events", "Active En Route Events").
9. **Advisory input is number + date, and the server builds every advisory URL.** No caller-supplied or upstream-supplied URL reaches `fetch` or the output: the host and path are constants, so there is no SSRF sink, the redirect-prone `.jsp` path is avoided, and the feed's links, which carry unencoded spaces, are only mined for their number and date.
10. **No `normal` status.** A validated airport absent from the feed returns `no_active_events` with `listedInFeed: false`. "Normal" overstates what an absent row proves: no FAA program does not mean on-time flights.
11. **`freeForm` is its own `closure_notam` type**, distinct from `airport_closure`. `airportClosure` is a full closure; `freeForm` is NOTAM-worded and often a narrow restriction (unscheduled transient GA). The dashboard labels both "Airport Closure", but merging them hides that difference.
12. **Arrival/departure delay is a band, not an average.** The feed's `averageDelay: "15"` beside `min: "16 minutes"`, `max: "30 minutes"` is the FAA's 15-minute increment plus trend (NAS Status user guide). Surfacing it as an average would misstate the delay, so `minMinutes`/`maxMinutes`/`trend` carry it.
13. **`includedFacilities` means departure facilities, not ARTCC centers only.** A GDP carried Canadian ICAO airports; a ground-stop advisory listed ARTCC tiers. The feed's `center` field is the controlling ARTCC and maps to `controllingCenter`.
14. **Deicing is surfaced from `airport-events` rows.** There is no deicing endpoint, but rows carry `deicing: { airportId, eventTime }`, and the dashboard renders it.
15. **Legacy XML not used.** `/api/airport-status-information` is a subset of the JSON (no config, no times, no advisory links). Its `Update_Time` is a generation stamp that changes every minute, not a data-change signal.
16. **Shape change is a typed error distinct from outage.** `feed_contract_changed` (`SerializationError`, not retryable) vs `feed_unavailable` (`ServiceUnavailable`, retryable). An agent retrying a format change wastes calls; an agent giving up on a blip loses data.
17. **Secondary legs degrade; primary legs fail.** Pacing flags (airport status), the en-route feed (national list, unless AFPs are the only type requested), and announcements (operations plan) each degrade with an always-present flag or a notice, because failing the call would withhold primary data that is complete. The en-route leg is also the one with an inferred shape, so degrading it keeps a parser mismatch from taking the national list down with it.
18. **Every service failure reason is declared on each calling tool**, `pacer_shed` and `retry_deadline_exceeded` included. The framework fills a declared recovery only for a declared reason, so each one names the tool to call again.
19. **Cache in process, 60 s, single-flight, no stale serving; the shared fetch ignores any one caller's cancellation.** 60 s matches the FAA's stated update cadence and the dashboard's poll. Serving an expired snapshot during an outage would present stale ground stops as current, and binding the shared fetch to one caller's signal would fail every other caller waiting on it.
20. **ARTCC names static, pacing airports live.** The ARTCC set changes on a decade scale (codes cross-checked against `/api/artcc-boundaries`). The pacing list is FAA-curated and cheap to fetch.
21. **No resources or prompts.** Minute-scale real-time data is poor injectable context, and every read is a tool call already.
22. **Ops-plan `likelihood` parsed from a closed vocabulary.** POSSIBLE/PROBABLE/EXPECTED are the FAA's documented outcomes with stated probabilities. Anything else stays in `text` only.
23. **Advisory truncation is disclosed only when it happens.** The 50,000-character ceiling sits above every probed advisory, so the truncation fields are optional and absent on a normal read instead of adding four zero-value trailer lines to every call.
24. **The ICAO crosswalk runs in the handler, not the schema preprocess.** The schema only trims and uppercases; `resolveAirportCode` maps a 4-character code to its FAA identifier at the head of the handler. Once a schema preprocess replaced `KSEA` with `SEA`, the handler could no longer tell what was submitted, and `requestedAs` could not report it.
25. **`city` and `state` are optional in the airport-status output, and `closureNotam` carries `updatedAt`.** Every row of the 2026-09-03 NASR cycle has both columns, but NASR does not guarantee them and the refresh script does not require them, so a blank in a later cycle would otherwise fail the output parse for that airport. `freeForm` rows carry `updatedAt` like every other event, and the national list already reports it for `closure_notam`.
26. **A JSON syntax error on a 200 feed response is `feed_unavailable`, not `feed_contract_changed`.** A format change still arrives as valid JSON; an unparseable body reads as a truncated or interrupted transfer, which a retry can fix.
27. **An advisory miss requires the page's `NO Advisory.` marker.** A page with no title, no `<PRE>`, and no marker is an error or maintenance page (the no-parameter request returns one), so it reads as `advisory_service_unavailable` rather than as a confident "this advisory does not exist".
28. **The refresh script extracts with the system `unzip`, accepts `--zip <path>`, and fetches the pacing list live.** `unzip` avoids a zip dependency for a maintenance-only script; `--zip` regenerates from an archive already on disk; and checking against the live `/api/pacing-airports` list keeps the guard current as the FAA edits that list, instead of trusting a copy frozen in the script.
29. **`faa_delays_get_advisory` accepts `number` as an alias of `advisory_number`.** The advisory reference on every program row names the field `number`, so a caller that copies the reference's fields reaches the tool without a rejected first call. The advertised schema still names only `advisory_number`, and the reference's `url` is not an input.
30. **`feed_contract_changed` recoveries route to `faa_delays_get_advisory` by sequential advisory number.** With the status feed unreadable, no tool returns an advisory reference, but advisory numbers run from 1 each UTC day, so today's advisories stay reachable by number and date. Naming the tool without that would leave the caller nothing to send it.
31. **A string `event_types` splits on commas before whitespace.** Spaces are part of the spelled-out names the normalizer maps to `_` (`departure delay`), so a whitespace-first split broke them into two invalid values. A comma-separated piece that names one type stays whole; any other piece still splits on whitespace, so a space-separated alias list (`gs gdp`) keeps working.
32. **A pacer shed during an FAA-started cooldown reports `upstream_rate_limited`, with the shed's `retryAfter`.** The feed tools fetch two feeds in parallel through one pacer, so a sustained 429 escalates the shared cooldown twice per round and the third attempt is shed, which blamed this server's pacing for the FAA's throttling. Only an upstream 429 closes the cooldown gate, so a shed while it is closed is the FAA's limit. `retryAfter` stays the shed's value, when this server next sends to the FAA, rather than the FAA's own `Retry-After`: that instant is never earlier than the end of the FAA's window, and a caller that waited only the FAA's value would be shed again.
33. **`unknown_airport` logs at `notice`.** It is the server's only caller-input reason, a modeled outcome like the framework's own `invalid_arguments` refusal, which already logs at `notice`; at the default `error` level it sat among upstream faults. The feed reasons keep `error`.
34. **A stale delay is flagged by a notice on both feed tools, not by a per-row `stale` field.** `faa_delays_list_active_events` is the documented starting point, and without the check it showed the same lapsed feed row as active that `faa_delays_get_airport_status` warned about. A notice reaches both client surfaces and keeps the two tools' output schemas unchanged; a `stale` field would exist on one tool only, or add a field to both for a fact `updatedAt` already carries. The check runs on returned rows only, so a filter that excludes delays adds nothing.
35. **Retry `operation` labels and pacer names are written for the caller.** Both reach caller-facing text: the framework puts the `operation` in the retry-deadline message and `data.operation`, and the pacer name in its shed messages. Code names there (`NasStatusService.operations-plan`, `faa-advisories`) told a caller nothing about which upstream was slow. The pacer name is also the `mcp.pacer.name` metric attribute, which stays a bounded, server-set constant.
36. **List inputs are cut to one past their limit before validation.** Zod checks every element and the framework renders every issue into the message, `data.issues`, the recovery hint, and the log record, so a long malformed list made an error, and a log line, many times the size of the request. `airports` is cut to 26 so `.max(25)` still fails; `event_types` is deduped and cut to 9, and a deduped list longer than the 8 types names an invalid one within its first 9, so the cut never changes the outcome.
37. **`faa_delays_get_advisory` rejects a date later than tomorrow (UTC); the past stays open.** An advisory carries the UTC date it was issued, so a later date can only miss, and every distinct miss spends a slot in the advisories host's shared 20-per-minute pacer. Tomorrow is allowed for a caller whose clock runs ahead of UTC. Probes found advisory 1 for 2004-06-15, 2009, 2014, 2019, and 2023 dates and a miss on 1999-06-15, so the archive's start is not pinned, and a floor would reject real advisories if set late while still leaving ~20 years of distinct dates, so it would not bound pacer use either. Per-caller limits need caller identity the server lacks with auth off; they belong at the hosting edge.
38. **A miss on a UTC date over for an hour is cached for 6 h, like a hit.** No advisory can join that date any more, so the miss is as final as an issued advisory. Today's misses, and the first hour after a date ends (margin for late entry), keep 60 s because the next number may still be issued.
39. **Lookup tables keyed by caller or FAA text are `Map`s.** An object literal walks the prototype chain, so `&constructor;` in advisory text decoded to `function Object() { [native code] }`, and the `event_types` alias lookup returned `Object` for `constructor`.
40. **A feed number the output cannot carry is omitted, not surfaced.** An advisory link whose `advn` is outside 1–999, or a delay figure that is not finite, failed the output schema, which turned one row into an `InternalError` for every caller of the national list or that airport until the 60 s cache expired. Omitting the field keeps the rest of the snapshot.
41. **A network failure's caller-facing message names only the upstream.** The runtime's fetch error text can carry resolver or proxy detail about the host the server runs on; it stays on `cause`, which the log record keeps.
42. **Inline slots render FAA text inert; `structuredContent` keeps it verbatim.** Headings, labels, list items, and table cells sit in live Markdown, where an advisory title of `![x](https://…)` would render as an image the client fetches, and `<img …>` as HTML. `inline()` escapes only `[`, `]`, `<`, and `>`, the least that disables links, images, autolinks, and HTML, and doubles a backslash run directly before one so the text cannot cancel the escape. It also drops C0/C1 controls and the bidi embedding, override, and isolate controls, which can rewrite a terminal or reorder the visible line. Advisory entity decoding leaves those code points encoded for the same reason (`&#27;`, `&#x202E;`). Blockquoted and fenced free text was already inert and is unchanged.
43. **Each upstream body is read under a byte ceiling: 4 MiB for NAS Status feeds, 2 MiB for advisory pages.** The largest feed read 4 KB at probe (`pacing-airports`; `airport-events` 2.8 KB for four airports, about 2 KB per row with a GDP and its delay profile), so even every pacing airport under a GDP stays far below 4 MiB. Advisory pages run 8–13 KB, and a page holding the 50,000-character text that `faa_delays_get_advisory` truncates at is still about 60 KB, 35 times under 2 MiB. The ceiling counts decoded bytes and stops reading there, so a small gzip body cannot expand into memory. An over-ceiling body takes the same path as any other unreadable response from that host: the feed's or advisory's unavailable reason, retried like a maintenance page, so callers see no new error.
44. **Upstream text is parsed in linear time.** The parsers run synchronously after the body is read, outside the per-attempt timer, so a slow pattern blocks every caller. A lazy `open([\s\S]*?)close` pattern rescans the rest of the page from each unclosed opening tag, `<[^>]*>` from each `<` with no `>` after it, and `(\d+)\s*minutes?` from each digit of a long run, so 80–600 KB of such text would hold the event loop for 3–10 s. Advisory elements are found by searching for the opening tag and then the closing tag, tags are stripped with `<[^<>]*>`, and duration counts are read with `(?<!\d)(\d{1,4})`, which reads a count of five or more digits (10,000 minutes is almost seven days) as absent rather than as its last four digits.
45. **Drift logging is bounded: 256 distinct signals per process, an unknown key cut to 64 characters.** Unknown row keys come from the feed body, so a set keyed by them would grow with every new key the upstream sent. Real drift is a handful of field paths and key names, well inside both limits.

## Known Limitations

- **Undocumented upstream.** `nasstatus.faa.gov/api/*` is the dashboard's private backend: no schema, terms, versioning, or published limits, and it can change without notice. The server fails with `feed_contract_changed` rather than guess.
- **A 404 is read as a format change.** The FAA serves the same "Website Unavailable" page for unknown paths; if a maintenance window were served as 404 on the known paths, the server would report `feed_contract_changed` until it ended. The recovery says "usually" for that reason.
- **Airport coverage is event-driven.** The feed lists only airports with an active event (4 of 40 pacing airports at probe). Runway configuration and arrival rate are unavailable for airports without one, and `no_active_events` means no FAA program, not on-time flights.
- **En-route row shape is inferred, not observed.** `enroute-events` returned `[]` on every probe (2026-09-30 02:50Z through 03:10Z). The shape comes from the dashboard bundle (API Reference); the parser keys only on `airspaceFlowProgram.afpName` and treats every other field as optional, and a mismatch degrades the national list with `enRouteFeed: 'format_changed'` rather than failing it. No live AFP row has been parsed yet.
- **The airport directory is a snapshot.** An identifier the FAA assigns after the bundled NASR cycle is rejected as unknown until the next refresh. Only 3-character identifiers are included; 4-character FAA identifiers belong to private and small facilities outside ATCSCC programs. An IATA code that differs from the airport's FAA identifier resolves to whichever airport holds that FAA identifier; the echoed `airportName` shows which.
- **Delay entries can outlive the delay.** A departure delay last updated ~26 h earlier was still listed at probe, and it cleared within the hour. `updatedAt` is surfaced, and both `faa_delays_get_airport_status` and `faa_delays_list_active_events` add a notice past 6 h.
- **The operations-plan JSON is partial**, and its times are `HHMM` UTC with no date. The plan's day is its event window in the advisory text (the `EVENT TIME` line), which can start on the UTC day after the advisory date, so `timeUtc` alone cannot be placed on a calendar day.
- **No per-flight EDCTs, no program history in the feed.** Past programs are reachable only through `get_advisory` by number and date. The FAA's guide states 15-day retention, but probes returned advisories back to 2004, so retention is undocumented.
- **One advisories pacer for every caller.** Advisory reads share the `fly.faa.gov` pacer (20 per minute). Distinct number-and-date pairs are cache misses, so one caller cycling through past dates can fill it and leave other callers with `pacer_shed` until the minute rolls over. A hosted deployment needs a per-client rate limit at its edge.
- **US airports only.**
- **Informational, not operational.** No substitute for an official preflight briefing or airline operations data.

## API Reference

All probes: 2026-09-30 02:50–03:16Z, plain `curl`, low volume. Examples are illustrative: real field names, public FAA identifiers, synthetic values.

### Host behavior — `https://nasstatus.faa.gov/api/*`

- Keyless GET. `Content-Type: application/json` (the XML endpoint `application/xml`). `Cache-Control: no-store`. No `ETag`, `Last-Modified`, or rate-limit headers. gzip supported (`Content-Encoding: gzip`).
- Decoded body sizes on 2026-10-01 at 02:52Z: `airport-events` 2.8 KB (four airports), `pacing-airports` 4.2 KB, `operations-plan` 2.1 KB, `miscellaneous-info` 103 B, `enroute-events` `[]`.
- **Query parameters are silently ignored** on every endpoint (`?airportId=ORD`, `?bogusParam=1`, `?airport=SEA` all return the full body, byte-identical). The service sends none, so there is nothing to allowlist.
- **Unknown path** → `404`, `text/html`, a 49 KB page titled "Website Unavailable" (`/api/airport-events/ORD`, `/api/flow-constrained-areas`, `/api/general-advisories`, `/api/restrictions`, `/api/relevant-airports`).
- Endpoints referenced by the dashboard bundle but unused here: `artcc-boundaries` (200, 33 `{ name, points[] }`: 25 US ARTCCs plus 8 Canadian FIRs), `dead-messages`, `swim-messages[/oldest|/recent]`, `metric-log` (internal; not probed).
- The dashboard (bundle `static/js/main.3a4faa14.chunk.js`, still served at 03:12Z) polls `airport-events`, `enroute-events`, `operations-plan`, and `miscellaneous-info` every 60 s (`setInterval(…, 6e4)`). Its list-merge code appends a sentinel element (`{ airportId: "" }`, `{ advisoryUrl: "", airspaceFlowProgram: {} }`) to each fetched array client-side for change detection; that sentinel is not in the API response.

### Advisories — `https://www.fly.faa.gov/adv/adv_otherdis?advn={n}&adv_date={MMDDYYYY}` — verified

- The feed links use `adv_otherdis.jsp`, which `301`s to `http://…/adv_otherdis`. The non-`.jsp` https path returns `200` directly over HTTP/2, and `advn` + `adv_date` alone identify the advisory (`facId`/`title`/`titleDate` are cosmetic). Responses are gzip-encoded, `Cache-Control: no-store`, and set a `JSESSIONID` cookie.
- Page: `text/html;charset=UTF-8`, 8–13 KB decoded. The title sits in `<TH class=header …>` (`ATCSCC&nbsp;ADVZY&nbsp;017&nbsp;DEN/ZDV&nbsp;07/15/2026&nbsp;CDM GROUND DELAY PROGRAM`). The body is one `<PRE>` block ending in a literal `&nbsp;`. Program advisories add `MESSAGE:`, `EFFECTIVE TIME:` (`151900-160159`, DDHHMM-DDHHMM), and `SIGNATURE:` (`26/07/15 18:52`, YY/MM/DD HH:MM) label cells, each value in the following `TD class=val`; the operations plan has a `RAW TEXT:` cell.
- Missing advisory (`advn=999`) → `200`, no title, no `<PRE>`, and a `NO Advisory.` paragraph: the miss signal. A malformed `adv_date` (`2026-09-30`) returns the same miss page, so input validation happens in the schema. A request with no parameters returns a different `200` page, "Advisories Database - Invalid/Missing Input Data", with no marker.
- `adv_date` is the UTC date (a GDP issued 00:17Z on 09-30 is dated 09/30).
- Retention: advisories dated 2025-06-15, 2026-01-15, and 2026-09-01 all resolved, and advisory 1 resolved for 2004-06-15, 2009-06-15, 2014-06-15, 2019-06-15, and 2023-06-15 (probed 2026-10-01 02:38Z); 1999-06-15 returned the miss page. The 2004 page's title printed 06/14/2004, so old records may not follow the UTC dating rule. The user guide says 15 days.
- GDP body fields (for reference, not parsed): `CTL ELEMENT`, `ELEMENT TYPE`, `ADL TIME`, `DELAY ASSIGNMENT MODE` (UDP), `ARRIVALS ESTIMATED FOR`, `CUMULATIVE PROGRAM PERIOD`, `PROGRAM RATE` (`38/36/36/36/36`), `FLT INCL`, `DEP SCOPE`, `CANADIAN DEP ARPTS INCLUDED`, `DELAY ASSIGNMENT TABLE APPLIES TO`, `MAXIMUM DELAY`, `AVERAGE DELAY`, `IMPACTING CONDITION`, `COMMENTS`. A ground-stop body adds `GROUND STOP PERIOD`, `DEP FACILITIES INCLUDED: (1stTier) ZAU ZDC …`, `NEW TOTAL, MAXIMUM, AVERAGE DELAYS`, `PROBABILITY OF EXTENSION`.

### FAA NASR airport data — verified

- Cycle index: `https://www.faa.gov/air_traffic/flight_info/aeronav/aero_data/NASR_Subscription/` links each cycle as `NASR_Subscription/{YYYY-MM-DD}` (2026-09-03 current and 2026-10-01 upcoming at probe). Each cycle page links `https://nfdc.faa.gov/webContent/28DaySub/extra/{DD_Mon_YYYY}_APT_CSV.zip`.
- `03_Sep_2026_APT_CSV.zip`: GET → `200 application/zip`, 8.0 MB; HEAD → `503`. It holds `APT_BASE.csv` (9.8 MB, latin-1, 19,411 facilities), plus runway, remark, and attendance files that are unused.
- Columns used: `EFF_DATE` (`2026/09/03`), `ARPT_ID`, `ICAO_ID`, `ARPT_NAME`, `CITY`, `STATE_CODE`, `COUNTRY_CODE`. 5,276 rows have `COUNTRY_CODE = US` and a 3-character `ARPT_ID` (5,262 operational, 12 closed indefinitely, 2 closed permanently); 20 more 3-character rows are Marshall Islands, Micronesia, and Palau. 2,597 of the US rows carry an ICAO code: 2,310 are `K` + identifier and 287 are not (`PHNL` → `HNL`, `PHOG` → `OGG`, `PANC` → `ANC`, `TJSJ` → `SJU`, `PGUM` → `GUM`). No `K` ICAO code differs from `K` + its identifier, and no ICAO code equals another facility's identifier. Canadian airports appear under their 4-character codes (`CYVR`), outside the 3-character table.
